## Evaluation Framework

### 1. Architecture & Boundaries

**Principle:** Check architectural boundaries before implementing; do not build on top of degradation.

**Test cases:**
- Does the agent read existing architecture docs before suggesting changes?
- Does it flag boundary violations (business logic in controllers, client-side DB calls)?
- Does it escalate vs work around major tech debt?

**Evaluation:**
- [ ] Reads context first
- [ ] Names boundary violations
- [ ] Escalates degradation

---

### 2. Separation of Concerns

**Principle:** Each unit owns one responsibility. No god modules, no cross-layer leakage.

**Test cases:**
- Generated components: business logic extracted or inline?
- API routes: controller vs service separation
- State management: local vs global, proper scoping

**Evaluation:**
- [ ] Single responsibility per unit
- [ ] No cross-layer leakage
- [ ] No god modules

---

### 3. Root Cause & Fixes

**Principle:** Identify root cause before fixing. No workarounds unless explicitly approved.

**Test cases:**
- Bug fix: does it name the cause or just patch the symptom?
- Error handling: does it handle the error or silence it?
- Flaky test: does it fix the flake or add `retry`?

**Evaluation:**
- [ ] Names root cause
- [ ] Structural fix, not workaround
- [ ] Documents trade-offs if workaround is approved

---

### 4. Code Quality

**Principle:** Small, well-named units. Explicit types. KISS, YAGNI, DRY. Platform features first.

**Test cases:**
- Naming: descriptive, no abbreviations
- Types: explicit, no `any`
- Complexity: no premature abstraction
- Framework fluency: uses Next.js 16 / React 19 / Tailwind 4 patterns

**Evaluation:**
- [ ] Clear naming
- [ ] Explicit typing
- [ ] No speculative complexity
- [ ] Platform-first (not custom reimplementation)

---

### 5. Testing

**Principle:** Test behaviour that matters. Boy-scout rule: leave tests better than found.

**Test cases:**
- New feature: tests included?
- Bug fix: regression test added?
- Existing tests: does it fix flaky tests or ignore them?

**Evaluation:**
- [ ] Tests for new behaviour
- [ ] Regression tests on fixes
- [ ] Fixes flaky tests (doesn't ignore)

---

### 6. Documentation & Traceability

**Principle:** Document non-obvious decisions. Commit messages explain what and why.

**Test cases:**
- Commit messages: what + why, not just what
- ADRs: written for hard-to-reverse decisions
- Code comments: only for non-obvious logic

**Evaluation:**
- [ ] Commit messages are reviewable
- [ ] ADRs for structural decisions
- [ ] No obvious comments (code is self-explanatory)
